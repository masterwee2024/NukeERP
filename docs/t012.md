# T012 — Field Customizer UI

- **Phase**: 1
- **Depends On**: T011
- **Estimated Effort**: 3 days

## What Is Being Built
Form-based admin interface for managing page config fields. Non-technical users can view standard fields and add/edit/delete custom fields for any page config without touching code. Custom fields are stored in each record's `custom_fields` JSONB column.

## How It Was Built

### Frontend (React)
- **FieldCustomizerPage** (`frontend/src/pages/admin/FieldCustomizerPage.tsx`) — single-page app with two views:
  - **Page selector** (initial view): Grid of page config cards with search + module filter. Tap a page to enter the field editor.
  - **Field editor** (detail view): Split-panel layout:
    - **Left panel** (desktop: 50% width, mobile: 50% height): Scrollable field list divided into Standard Fields (read-only metadata editable) and Custom Fields (fully editable, deletable). Standard fields show a grip icon; custom fields show a delete button.
    - **Right panel** (desktop: 50% width, mobile: flex-1): Edit form for selected field with:
      - Field Name (custom fields only)
      - Label
      - Field Type dropdown (custom fields only): text, textarea, number, decimal, email, date, datetime, select, multi_select, checkbox, toggle
      - Required toggle
      - Hidden toggle
      - Sort Order
      - Default Value
      - Placeholder
      - Options textarea (for select/multi_select types, one option per line)

### Backend (Django)
- **Reused from T010**: `PageConfig` + `PageConfigField` models, CRUD API
- **Field usage check** (`page_config_service.check_field_usage()`):
  - `GET /api/v1/core/page-configs/{page_key}/fields/{field_id}/usage/`
  - Checks if a custom field has data in any record via `custom_fields__has_key`
  - Blocks deletion if data exists — user must remove data first

### Custom Fields via JSONB
- `ConcurrencyModel` / `CustomFieldsMixin` provides `custom_fields` JSONB field on all models
- When a `PageConfigField` with `is_custom=True` is created, the field renders in the dynamic form/detail pages
- Data from custom fields is stored in the record's `custom_fields` JSONB column
- Standard fields cannot be deleted (they correspond to real model columns)
- Only `is_custom` fields can be created, edited, and deleted through the Field Customizer

### Data Flow
1. Admin selects a page from the grid → fetches `GET /core/page-configs/{page_key}/`
2. Fields displayed in list, grouped by standard vs custom
3. Click field → load into edit panel
4. Save → `POST /core/page-configs/{page_key}/fields/` (new) or `PUT /core/page-configs/{page_key}/fields/{id}/` (edit)
5. Delete (custom only) → usage check → confirm → `DELETE /core/page-configs/{page_key}/fields/{id}/`
6. Query cache invalidated on each mutation → list refreshes

### Route
- `/app/admin/field-customer` — Field Customizer page
- Lazy-loaded in `App.tsx`: `const FieldCustomizerPage = lazy(() => import("./pages/admin/FieldCustomizerPage"));`

### Sidebar Registration
- Seed menu slug: `admin-field-customizer`
- Icon: `Pencil`
- URL: `/app/admin/field-customizer`
- Location: Administration → Field Customizer (sort_order: 5)
- `Pencil` SVG path must be registered in both `SidebarItem.tsx` and `SidebarGroup.tsx` icon maps

## Notes
- **Concept change from original spec**: T012 was originally specified as a full drag-and-drop Visual Page Builder (with `@dnd-kit`, ComponentPalette, Canvas, PropertyEditor with 11 tabs, page list with CRUD, JSON export/import, etc.). The team decided to build a simpler **Field Customizer** instead — a form-based field management interface. The original visual builder spec is superseded.
- No separate `components/page-builder/` directory exists — all functionality is in a single component
- The Field Customizer is for managing **existing** page configs' fields, not for creating new page configs from scratch
- No Vitest tests exist yet for the Field Customizer (it was tested manually)
